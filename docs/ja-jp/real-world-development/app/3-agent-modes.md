プロジェクトに小さな機能を追加しました。より大きな変更には、さらにしっかりしたプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って動作できるため、適切なものを適切な方法で構築できます。このレッスンから複数のレッスンにわたり、エージェント主導の一般的な開発プロセスを進めます。Issue を使って新機能を作成し、コードの妥当性と機能の動作を確認して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使います。通常は作業するファイル タイプごとに別のセッションや PR を使いますが、ここでは中心的な概念に集中できるよう手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加し、QA エージェントを作成して、機能 PR を作成します。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がカテゴリやパブリッシャーでゲームを絞り込める必要があります。バックログの Issue には機能が記載されていますが、カテゴリの組み合わせ方など、実装前に合意すべき詳細があります。Plan モードで決定事項を整理してから、範囲を定めた実装を Autopilot に任せます。

## 背景

AI コーディング エージェントを開発ワークフローに取り入れても、基本は変わりません。むしろ基本がさらに重要になります。多くの開発者は次のような手順で作業します。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 構築するものの計画を作成します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プル リクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な手順はチームや組織によって異なりますが、多くは上記の流れを基本としています。

この標準的なアプローチに従うと、AI が生成したコードも要件を満たし、手作業で作成したコードと同じ確認プロセスを経るようにできます。

## セッション モード

**セッション モード**では、エージェントにどの程度の自律性を与えるかを設定します。プロンプト欄の下にあるドロップダウンから選択でき、いつでも変更できます。

- **Interactive:** エージェントと一緒に作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan:** エージェントが先に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot:** エージェントが完全に自律してコードを作成し、テストを実行し、入力を待たずに反復します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** を開きます。テンプレートで用意された Issue のため、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

   ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード セレクターから **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行させます。ターミナルでは成功するのにセッションで失敗する場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチを確認できます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリとパブリッシャーによる絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認します。複数のカテゴリをどう組み合わせるか、ゲームが一致しない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。承認前に計画の修正を依頼し、後の検証に使えるよう Issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** または使用中のバージョンで同等の項目を選択します。承認によってモードが切り替わったと思い込まず、アクティブなモードを確認してください。モード表示が **Autopilot** であることを確かめます。

Copilot は実装を開始し、確定した計画に沿って反復しながらコードを生成してテストを実行します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューします。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリとパブリッシャーの組み合わせも含め、結果を Issue と承認済みの補足事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を採用する前に失敗を解決し、影響するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカル サーバーを再利用する場合があります。テスト対象が以前のレッスンのサーバーではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がなさそうでも、実際に動作するかを確認します。アプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザー キャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果がそのカテゴリに一致することを確認します。フィルターを解除してからパブリッシャーを選び、結果がそのパブリッシャーに一致することを確認します。
4. カテゴリとパブリッシャーを組み合わせ、結果を Issue と承認済みの計画に照らし合わせます。複数カテゴリをサポートする場合は、合意した組み合わせ動作を検証します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確かめます。
6. 確認が終わったら、次のプロンプトでこのセッションの開発サーバーを停止します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

まだフィルター機能の PR を作成したりマージしたりしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次はフィルター機能のコードにカスタム指示を適用し、その後スキルと QA の改善を加えてから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後、セッションはそのままにしておき、次のレッスンで再開します。
